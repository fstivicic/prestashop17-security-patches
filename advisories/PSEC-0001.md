# PSEC-0001 — Stored XSS in the back-office customer service view

| | |
|---|---|
| **CVE** | CVE-2026-44212 |
| **Upstream advisory** | [GHSA-w9f3-qc75-qgx9](https://github.com/advisories/GHSA-w9f3-qc75-qgx9) |
| **Severity** | Critical (upstream rating) |
| **Upstream affected** | PrestaShop `< 8.2.6`, `>= 9.0.0 < 9.1.1` |
| **Verified on** | PrestaShop 1.7.8.11 — **confirmed vulnerable** |
| **File** | `admin-dev/themes/default/template/controllers/customer_threads/helpers/view/view.tpl` |
| **Patch** | `patches/0001-*.patch` |

## Why 1.7 is affected when the range does not say so

The published range is `< 8.2.6`. Numerically that includes every 1.7 release,
but PrestaShop stopped shipping security fixes for 1.7 with the release of
PrestaShop 9 in June 2025, and the last 1.7 release was `1.7.8.11` in January
2024. So the range covers 1.7 while no fix for 1.7 exists, and there is no
extended support programme to buy one from.

That makes this different from the usual EOL situation. Nobody has to be
persuaded that 1.7 is in scope. The vendor's own range says it is. There is
simply nothing shipped.

## The vulnerability

An **unauthenticated** visitor submits the public Contact Us form with a
payload in the email field. The value is stored, and later rendered without
escaping when a back-office employee opens that customer thread. Upstream
describes the result as session hijacking and full back-office takeover.

Two sites in the template render the value unescaped. From a pristine
`1.7.8.11` tree:

```smarty
line 100:  {else} {$thread->email}{/if}</h3>
line 121:  <input type="hidden" name="msg_email" value="{$thread->email}" />
```

Line 121 is the more dangerous of the two: the value lands inside a
double-quoted attribute, so a payload containing `"` terminates the attribute
and everything after it is parsed as further attributes.

**This is an oversight, not a convention.** The same template escapes the same
value correctly thirty lines earlier:

```smarty
line 64:   <h2>{$thread->email|escape:'html':'UTF-8'}</h2>
```

Three render sites, one escaped, two not.

## Proof

From `tests/probe.php` against a stock 1.7.8.11 tree:

```
CVE-2026-44212/thread-email-escaped        VULNERABLE  unescaped at line 100, line 121
CVE-2026-44212/control-h2-already-escaped  FIXED       escaped at line 64
```

The second line is the control. If it ever fails, the probe is reading the
wrong file: that `<h2>` has been escaped in every version.

After the patch:

```
CVE-2026-44212/thread-email-escaped        FIXED  all 3 occurrence(s) escaped
CVE-2026-44212/control-h2-already-escaped  FIXED  escaped at line 64, line 100, line 121
```

## The fix

Identical to the change upstream shipped in 8.2.6 and 9.1.1. The escape filter
and its syntax are unchanged between 1.7 and 8.x, so this is a true backport
with no adaptation:

```diff
-{else} {$thread->email}{/if}</h3>
+{else} {$thread->email|escape:'html':'UTF-8'}{/if}</h3>

-<input type="hidden" name="msg_email" value="{$thread->email}" />
+<input type="hidden" name="msg_email" value="{$thread->email|escape:'html':'UTF-8'}" />
```

## What is deliberately **not** backported

Upstream's 8.2.6 release also changed `classes/Validate.php`:

```diff
 $errors = $validator->validate($email, new Email([
-    'mode' => 'loose',
+    'mode' => 'strict',
 ]));
```

**That cannot be backported as written, and should not be approximated.**
PrestaShop 1.7 does not use Symfony's email validator here. It uses
`egulias/EmailValidator`:

```php
public static function isEmail($email)
{
    return !empty($email) && (new EmailValidator())->isValid($email, new MultipleValidationWithAnd([
        new RFCValidation(),
        new SwiftMailerValidation(),
    ]));
}
```

There is no loose/strict mode to flip. Producing an equivalent would mean
choosing a different validation strategy, which changes behaviour for **every
email field on the site** — customer registration, newsletter, order contact,
employee accounts. That is a behaviour change dressed as a security patch, and
it is exactly the kind of thing that breaks a merchant's signup flow a week
after they apply a patch they were told was safe.

The escaping fix closes the vulnerability on its own. The validation change was
defence in depth. The probe reports the 1.7 validator shape as a **note** so
the gap is visible rather than silently absent.

Also not backported: the same release removed a stray `c` character from the
admin login template. Cosmetic, unrelated to this CVE.

## Behaviour change

Email addresses shown in the customer service view are now HTML-escaped. An
address containing `<`, `>`, `"` or `'` renders as entities rather than raw
markup. `tests/regression.php` confirms that ordinary addresses — including
apostrophes (`o'brien@example.ie`) and non-ASCII (`ünicode@example.com`) —
still decode back to exactly what was submitted.

## Limits of this verification

- **The proof is template analysis, not exploitation.** The probe checks that
  every render site applies an escape filter. It does not stand up PrestaShop,
  submit the Contact Us form and open the thread as an employee. That would be
  stronger and has not been done.
- **The regression harness is not Smarty.** It evaluates only the constructs
  this template uses. It catches brace and filter damage from hand-editing,
  which is the realistic failure mode, but it is not a compiler.
- **Only this template was examined.** Other unescaped renderings of
  attacker-controllable values elsewhere in the 1.7 back office are likely and
  were not searched for.
- **1.7.8.11 only.** Earlier 1.7.x releases almost certainly share the defect
  but were not checked, and the patch may not apply to them cleanly.
